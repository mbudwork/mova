## Этап 0. Два блокера, которые нужно знать до начала

Проверил архив перед тем, как писать инструкцию. Два места, на которых
деплой сломался бы или тихо сделал не то.

### 0.1. Сборка падала на ошибке типов

```
src/lib/audio/provider.ts(78,24): error TS2345:
  Argument of type 'string | null' is not assignable to parameter of type 'string'.
```

`next.config.ts` содержит `typescript: { ignoreBuildErrors: false }` — значит
`next build` на этой ошибке останавливается, и Netlify выдал бы failed deploy.

Причина настоящая, а не формальная: `audio_assets.storage_path` в схеме
nullable, потому что строка манифеста создаётся раньше, чем появляется файл.
Такая строка — не воспроизводимый трек, и обрабатывать её надо как отсутствие
трека. Исправлено так:

```diff
-    if (error || !asset) return null;
+    // storage_path is nullable in the schema: a row can exist as a manifest
+    // entry before any file is generated. Such a row is not a playable track,
+    // so it is treated exactly like a missing one.
+    if (error || !asset?.storage_path) return null;
```

После правки `npm run typecheck` чистый, `npm run build` проходит,
29 юнит-тестов зелёные — проверил локально.

### 0.2. На Netlify не работает `vercel.json`

В репозитории есть `vercel.json`, и в нём три заголовка, включая
`X-Robots-Tag: noindex, nofollow, noarchive`. Netlify этот файл не читает
вообще. То есть review-сборка на Netlify была бы открыта для индексации,
хотя в коде защита стоит.

Добавлен `netlify.toml` с теми же заголовками, командой сборки и пином
Node 22. Второй слой защиты (`src/app/robots.ts` с `Disallow: /`) работал и
раньше — но одного robots.txt мало, краулер может его проигнорировать.

## Этап 2. Заменить содержимое репозитория

Смысл: старая версия должна уйти целиком, а не «слиться» с новой, иначе
останутся файлы, которых в новой версии нет. При этом история коммитов
сохраняется — откатиться можно всегда.

```bash
# 1. Клонируем текущий репозиторий (не поверх старой рабочей копии)
git clone git@github.com:<ваш-аккаунт>/<репозиторий>.git mova-repo
cd mova-repo

# 2. Страховка: ветка с текущим состоянием, чтобы откат был одной командой
git branch backup-before-v2

# 3. Сносим всё отслеживаемое, кроме .git
git rm -r --cached . -q
find . -mindepth 1 -maxdepth 1 ! -name '.git' -exec rm -rf {} +

# 4. Кладём новую версию (содержимое папки, не саму папку)
cp -R /путь/к/mova-deploy-ready/. .

# 5. Проверяем глазами, что именно меняется
git add -A
git status
```

На шаге 5 в списке не должно быть ни `node_modules/`, ни `.next/`, ни
`.env` — они закрыты в `.gitignore`. Если что-то из этого появилось,
останавливайтесь и разбирайтесь: `.env` в публичном репозитории означает
скомпрометированный `service_role` ключ.

```bash
# 6. Локальная проверка до пуша — дешевле, чем красный деплой
npm ci
npm run typecheck
npm run test:unit

# 7. Коммит и пуш
git commit -m "MOVA v2: merged codebase, content candidate migrations, netlify config"
git push origin main
```

Если основная ветка называется не `main`, подставьте своё имя.

## Этап 3. Netlify: переменные окружения

Ставится **до** редеплоя. Без них приложение не стартует: `src/lib/config/env.ts`
валидирует окружение при загрузке модуля и бросает исключение, если чего-то
не хватает.

Netlify → ваш сайт → **Site configuration → Environment variables**.

| Переменная | Значение | Secret |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | `https://vcayatyamthyzeycfshc.supabase.co` | нет |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon-ключ проекта MOVA (JWT, начинается с `eyJ`) | нет |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role ключ | **да** |
| `NEXT_PUBLIC_SITE_URL` | боевой URL сайта, например `https://mova.netlify.app` | нет |

Оба ключа: Supabase → проект MOVA → **Project Settings → API Keys**.

Чего ставить **не** надо:

- `STRIPE_*` — пусто, оплата остаётся в mock-режиме и чекаут выключен.
- `ELEVENLABS_API_KEY` — пусто, аудио честно показывает «ещё не записано».
- `NEXT_PUBLIC_CHECKOUT_ENABLED` — не ставьте `true`. Логика в `env.ts` такая:
  если чекаут объявлен работающим, а Stripe в моке, приложение отказывается
  стартовать. Это правильно — mock-провайдер выдал бы FULL_ACCESS без оплаты.
- `ALLOW_DEMO_MODE_IN_PRODUCTION` — нужен только чтобы обойти ту самую
  защиту. Пока чекаут выключен, переменная не нужна.

Если раньше эти переменные уже стояли на старом деплое — сверьте, что
`NEXT_PUBLIC_SUPABASE_URL` указывает именно на `vcayatyamthyzeycfshc`, а не
на какой-нибудь предыдущий проект.

## Этап 4. Редеплой и проверка

Пуш в `main` запускает сборку автоматически. Если сайт ещё не связан с
репозиторием: Netlify → **Add new site → Import an existing project** → GitHub
→ ваш репозиторий. Build command и publish directory Netlify возьмёт из
`netlify.toml`, вручную вводить не нужно.

Что смотреть в логе сборки:

1. `Next.js Runtime` подхватился (Netlify ставит его сам, увидев `next` в
   зависимостях).
2. Сборка дошла до таблицы маршрутов — их 30, из них `/`, `/ru`, `/uk`,
   `/app/*` динамические, `/login`, `/register`, `/legal/*`, `/robots.txt`
   статические.
3. Предупреждение `[env] Building for production without Stripe/ElevenLabs
   keys` — **это норма**, так и задумано.

После деплоя, руками:

```bash
curl -sI https://<ваш-домен>/ | grep -i x-robots-tag
# ожидаем: x-robots-tag: noindex, nofollow, noarchive
```

Дальше в браузере: открыть `/ru` (лендинг с цифрами курса — там должно быть
404 фразы и 43 урока, то есть ровно как до импорта), залогиниться, пройти
один урок. Если урок открывается и фразы отдаются — связка приложение ↔
Supabase живая.

## Этап 5. Supabase CLI — отдельная проблема, деплою не мешает

Разошлась история миграций. В базе версии записаны такие, какими их
проставила панель, и они **не совпадают** с именами файлов в репозитории:

| Файл в репозитории | Запись в базе |
|---|---|
| `20260823000100_content_model.sql` | `20260905164554 content_model` |
| `20260823000800_course_engine_v2.sql` | `20260906124820 course_engine_v2` |
| … и так все 11 старых | … |

Практический смысл: **не запускайте `supabase db push`** из репозитория как
есть. CLI решит, что ни одна из 11 старых миграций не применена, и попробует
накатить их заново — на живой базе это в лучшем случае набор ошибок
«relation already exists», в худшем — испорченные данные.

Три новые миграции я специально назвал теми же версиями, что уже записаны в
базе (`20260906155919`, `20260906160013`, `20260906160055`), так что их CLI
пропустит.

Чтобы починить историю раз и навсегда, после `supabase link`:

```bash
for v in 20260823000100 20260823000200 20260823000250 20260823000300 \
         20260823000400 20260823000500 20260823000600 20260823000700 \
         20260823000800 20260823000900 20260905000100; do
  npx supabase migration repair --status applied "$v"
done
```

Команда ничего не выполняет в базе — только помечает эти версии как уже
применённые в журнале. После этого `supabase db push` станет безопасным и
будет накатывать только по-настоящему новые миграции.

Netlify миграции не запускает, так что на деплой это никак не влияет —
делать можно когда удобно.

## Этап 6. Позже: публикация контента

Когда native reviewer и Facharbeiter закроют свои списки — `ops/promote-content-candidate.sql`.
Порядок шагов внутри важен: сначала фразы становятся approved, только потом
уроки публикуются. Наоборот — и урок отрендерится пустым, потому что RLS не
отдаст неодобренные фразы.

Safety-блок (14 фраз: пять правил VDE 0105-100 и цепочка по газу) там
закомментирован намеренно и требует отдельного ревью. Пока он закрыт, уроки
E15 и S12 не опубликуются — это условие в шаге 4, а не сбой.

До публикации стоит поправить `speaker` у recognition-фраз: сейчас у всех
121 стоит `bauleiter`, потому что в новом воркбуке колонки Speaker нет.
В уроках E15 и S12 говорит Elektrofachkraft или коллега, и «кто это
говорит» там — половина смысла.
