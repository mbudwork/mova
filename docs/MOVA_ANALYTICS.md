# MOVA — ANALYTICS

## Зачем

Один вопрос, ради которого построено всё остальное:

```
Посетители → начали тест → прошли тест → нажали покупку → оплатили
```

с разрезом по кампании, креативу и дню. Всё, что не помогает ответить на этот
вопрос, в MVP не строится.

## Идентификаторы

| Поле | Живёт | Зачем |
|---|---|---|
| `anonymous_id` | localStorage, навсегда | Связать покупку на третьей неделе с креативом первой |
| `session_id` | sessionStorage, до закрытия вкладки | Отличить «начал тест дважды» от двух людей |
| `user_id` | из сессии на сервере | Появляется после регистрации |

**First touch выигрывает.** UTM записываются при первом визите и не
перезаписываются при возврате по прямой ссылке — иначе кампания, приведшая
человека, потеряется в момент покупки.

## События

| Событие | Когда |
|---|---|
| `landing_view` | Загрузка лендинга, один раз за загрузку |
| `hero_test_click` | Любая кнопка перехода к тесту (`placement` в свойствах) |
| `demo_audio_play` | Ответ в мини-пробе на лендинге |
| `test_started` | Открыт первый вопрос |
| `test_question_answered` | Каждый ответ: `position`, `correct`, `skill` |
| `test_completed` | Показан результат |
| `test_result_viewed` | Экран результата отрисован |
| `pricing_viewed` | Блок покупки попал в вьюпорт (40%) |
| `purchase_clicked` | Нажата кнопка доступа |
| `checkout_started` | Оформление начато (PHASE 9) |
| `purchase_completed` | Оплата подтверждена вебхуком (PHASE 9) |
| `login` | Успешный вход |
| `onboarding_started` / `onboarding_completed` | Онбординг |
| `lesson_started` / `lesson_completed` | Занятие |
| `pwa_install_prompt_viewed` / `pwa_install_instruction_opened` | Установка на экран |

Имена перечислены в `src/lib/analytics/events.ts`. Опечатка становится ошибкой
типов, а не дырой в отчёте.

## Защита от дублей

Два уровня:

1. Клиент: `track(event, props, { once: true })` — набор уже отправленных
   ключей на загрузку страницы. Ре-рендер не удваивает `landing_view`.
2. Секции отслеживаются через `IntersectionObserver` с `disconnect()` после
   первого срабатывания, а не при монтировании.

## Что решает сервер, а не клиент

`/api/track` — не прокси. Он:

- сверяет имя события со списком известных, иначе 400;
- обрезает все строки до 200 символов;
- берёт `user_id` **из сессии**, а не из тела запроса;
- нормализует `device_category` до трёх значений;
- никогда не возвращает ошибку, ломающую страницу: аналитика не продукт.

Браузер не может записать событие от чужого имени.

## Что не собираем

Ни почты, ни имени, ни IP, ни отпечатка браузера в событиях. `anonymous_id` —
случайный UUID без связи с личностью. Ответы теста хранятся как
`correct: true/false` и навык, без содержания.

## Meta Pixel и Conversions API

Архитектура готова, интеграция не включена. Pixel ID и токен CAPI читаются из
переменных окружения; пока они пусты, ничего не грузится и никаких запросов не
уходит. Ключевые конверсии для Meta — `test_completed`, `purchase_clicked`,
`purchase_completed`; серверные события CAPI будут отправляться из того же
`/api/track`, где уже есть `anonymous_id` и UTM для дедупликации с Pixel.

Учётных данных в репозитории нет и быть не должно.

## Owner-отчёт

`/admin/funnel` — одна страница, только для роли admin. Считает
`funnel_summary()` в БД. Это не BI: когда страница перестанет отвечать на
главный вопрос, надо экспортировать данные во внешний инструмент, а не
наращивать её.

## Ограничения

- Блокировщики рекламы режут часть событий. Абсолютные числа занижены,
  соотношения между кампаниями — нет.
- В приватном режиме `localStorage` недоступен, `anonymous_id` живёт одну
  сессию.
- `purchase_completed` появится только с PHASE 9.
