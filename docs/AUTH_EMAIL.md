# Подтверждение почты и отправитель писем

## Что было сломано

Цепочка, из-за которой пользователь не мог войти после регистрации:

1. `/register` → `signUp()` вызывает `supabase.auth.signUp()`.
2. При включённом «Confirm email» Supabase возвращает **пользователя без
   сессии**: аккаунт создан, но до перехода по ссылке из письма он не работает.
3. Старый код проверял только `error` и в любом случае делал
   `redirect('/onboarding')`.
4. `proxy.ts` видит анонимный запрос на защищённый маршрут и отправляет на
   `/login?next=/onboarding`.
5. Пользователь оказывается на форме входа, ничего не понимая. Про письмо ему
   нигде не сказали.
6. Он вводит правильный пароль. Supabase возвращает `email_not_confirmed`, но
   `signIn()` схлопывал любую ошибку в «Почта или пароль не подходят».

То есть система дважды соврала: сначала промолчала про письмо, потом назвала
верный пароль неверным.

## Что исправлено в коде

| Файл | Правка |
|---|---|
| `src/app/auth/actions.ts` | `signUp` проверяет `data.session`; если её нет — `/register/check-email`, а не `/onboarding` |
| | `signIn` отдельно обрабатывает `email_not_confirmed` вместо «пароль не подходит» |
| | добавлен `emailRedirectTo` — без него ссылка в письме ведёт на Site URL из панели |
| | добавлен `resendConfirmation()` — повторная отправка письма |
| | `signIn` уважает `next`, с защитой от открытого редиректа (`//evil.com`) |
| `src/app/register/check-email/` | новый экран «проверь почту» + форма повторной отправки |
| `src/components/AuthForm.tsx` | неподтверждённая почта показывается синим, с ссылкой на повтор, а не красной ошибкой |
| `src/app/login/page.tsx` | показывает причину, когда ссылка из письма протухла (`?error=expired_link`) |

Про `emailRedirectTo` отдельно: раньше его не было вообще, и Supabase
подставлял Site URL из настроек проекта. На свежем проекте там
`http://localhost:3000` — то есть даже те письма, что доходили, вели в никуда.

Экран `/register/check-email` намеренно одинаково отвечает на три разных
случая: новый аккаунт, адрес уже зарегистрирован, письмо потерялось. Различать
их на экране нельзя — это дало бы любому проверять, какие адреса есть в базе.
Supabase по той же причине возвращает при повторной регистрации пользователя
с пустым `identities`.

## Обязательная настройка в панели Supabase

Без неё правки в коде не помогут: ссылка в письме всё равно будет вести не туда.

**Authentication → URL Configuration**

| Поле | Значение |
|---|---|
| Site URL | `https://mbud.de` |
| Redirect URLs | `https://mbud.de/auth/callback` |

Если пользуетесь deploy preview на Netlify, добавьте туда же
`https://*--<имя-сайта>.netlify.app/auth/callback` — иначе на превью
подтверждение работать не будет.

## Отправитель письма — два варианта

Сейчас письмо приходит от `noreply@mail.app.supabase.io`. Это встроенный
сервис Supabase, и он не предназначен для боевого использования: жёсткий лимит
на количество писем в час и высокая доля попаданий в спам. Для аудитории,
которая читает почту с телефона на объекте, это означает, что часть людей
письмо просто не увидит.

### Вариант A — выключить подтверждение почты

**Authentication → Sign In / Providers → Email → Confirm email: OFF**

`signUp` сразу возвращает сессию, пользователь попадает в онбординг, писем нет
вообще. Самый короткий путь к работающей регистрации, и для курса, который
продаётся строителям, лишний шаг с почтой — это реальный отвал на воронке.

Код к этому уже готов: ветка `if (!data.session)` просто перестанет
срабатывать, ничего переписывать не нужно.

Чем платите: почта никем не проверена. Опечатка в адресе — и человек не сможет
восстановить пароль, а вы не сможете с ним связаться. Для платного продукта
это заметный риск, потому что адрес — единственный способ связи с покупателем.

### Вариант B — свой SMTP, письма с mbud.de

**Project Settings → Authentication → SMTP Settings → Enable Custom SMTP**

Нужен транзакционный провайдер — Resend, Postmark, Brevo, Amazon SES. В
настройках указывается хост, порт, логин, пароль и адрес отправителя, например
`noreply@mbud.de`, имя отправителя `MOVA`.

На домене mbud.de при этом придётся прописать DNS-записи, которые даёт
провайдер: SPF, DKIM и желательно DMARC. Без них письмо с обратным адресом
`@mbud.de`, отправленное чужим сервером, для Gmail выглядит как подделка и
уходит в спам вернее, чем письмо от самого Supabase.

Шаблон письма правится в **Authentication → Email Templates → Confirm signup**.
Стандартный — на английском, что для русскоязычной аудитории само по себе
выглядит подозрительно. Минимальная замена:

```html
<h2>Подтверди почту</h2>
<p>Ты зарегистрировался на MOVA — немецкий для стройки.</p>
<p>Нажми кнопку, чтобы подтвердить адрес и начать первый урок:</p>
<p><a href="{{ .ConfirmationURL }}">Подтвердить почту</a></p>
<p>Если это был не ты — просто удали письмо, ничего не произойдёт.</p>
```

### Выбрано: вариант A

Подтверждение почты выключается. Порядок действий — этап 3.5 в
`docs/DEPLOY_V2.md`.

Код к этому готов и менять его не нужно: `signUp` получает сессию сразу, ветка
`if (!data.session)` перестаёт срабатывать, экран `/register/check-email`
остаётся в проекте и продолжает обслуживать повторную отправку — он
понадобится, если подтверждение когда-нибудь включат обратно, и ничего не
стоит, пока не открыт.

SMTP на mbud.de (B) остаётся сделать до появления платящих пользователей.

Причина, по которой B всё равно понадобится: восстановление пароля. Это письмо
отправляется всегда, независимо от того, включено подтверждение или нет, и
идёт через тот же встроенный сервис с теми же лимитами и тем же спамом. Как
только у вас появится первый пользователь, забывший пароль, встроенный
отправитель станет проблемой.

Порядок между A и B значения не имеет — они независимы. Можно поднять SMTP и
оставить подтверждение включённым; тогда письма пойдут с mbud.de сразу.
